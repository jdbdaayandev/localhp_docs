LocalPHP is a small MVC-oriented PHP framework with routing, controllers, views, database tools, sessions, CSRF protection, and a command-line workflow for local projects.

Documentation overview

This guide documents the framework included in this project archive. It describes the public APIs and the intended workflow, while distinguishing development conveniences from production requirements.

Scope: LocalPHP is currently a lightweight framework, not a drop-in replacement for Laravel or CodeIgniter. The included database layer targets MySQL/MariaDB. Review the source and test behavior before using it for sensitive or public-facing systems.

Requirements

  • PHP 8.2 or newer.
  • Composer autoloader; the project archive includes a vendor/ directory.
  • MySQL or MariaDB and the PHP PDO MySQL extension for database features.
  • Apache with mod_rewrite and overrides enabled for the root localhost rewrite option.

Routes and pages that do not use the database can run without an active MySQL connection because database connections are created lazily.

Install and run

Option A — XAMPP / Laragon

  1. Extract the archive into your web root, for example htdocs/localphp.
  2. Start Apache. Start MySQL too if the application uses database features.
  3. Set APP_URL=http://localhost/localphp in .env.
  4. Open http://localhost/localphp. The root .htaccess forwards requests to public/.

Option B — PHP development server

php local serve
# Custom host and port
php local serve 127.0.0.1:8080

Open the URL printed in the terminal. The server document root is public/, so application URLs do not include /public.

Development only: PHP's built-in server is not intended for production traffic. For deployed environments, configure Apache or Nginx to use public/ as the document root.

Routing

Declare routes in routes/web.php using the router provided to the route file. Supported registration methods are get, post, put, and delete.

$router->get('/status', function () {
    return response(['success' => true, 'message' => 'LocalPHP is running']);
});

$router->post('/api/profile', function ($request) {
    return json([
        'success' => true,
        'data' => ['name' => $request->input('name')],
    ], 201);
});

Named routes and parameters

Route objects support name(), URI matching, and extraction of route parameters. Use route patterns as implemented in framework/src/Routing/Route.php; verify optional or wildcard syntax against the current implementation rather than assuming Laravel-compatible syntax.

Dispatch behavior

The router matches the incoming request to a route, executes a closure or controller action, and normalizes the result into a response. Supported results include a Response instance, a string, or an array (serialized as JSON by the router's response conversion).

Controllers

Controllers live in app/Controllers/. The included HomeController demonstrates an action method. Generate a controller with:

php local make:controller HomeController

Use controller methods to coordinate request input, application logic, models, and a response. Keep SQL and large data operations out of templates. Confirm the action format supported by the router when wiring a controller route.

// Example action shape
public function index()
{
    return view('home', ['title' => 'Dashboard']);
}

Requests and responses

Request object

The request object wraps the HTTP method, URI, base path, query parameters, input, uploaded files, cookies, server values, and headers. JSON request bodies are decoded for input access where the request implementation supports them.

$name = $request->input('name');
$page = $request->query('page', 1);
$file = $request->file('attachment');
$acceptsJson = $request->expectsJson();

Response helpers

return json(['message' => 'Created'], 201);

return json(['message' => 'Not found'], 404, [
    'Cache-Control' => 'no-store',
]);

return response('<h1>Hello</h1>', 200);

The Response object exposes content, status code, headers, fluent status/header setters, and send(). Use appropriate HTTP statuses: 200 OK, 201 Created, 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 419 CSRF mismatch, and 422 validation failure when applicable.

Views and templates

Views are stored under resources/views/. Render one with the view() helper:

return view('home', [
    'title' => 'Products',
    'products' => $products,
]);

LocalPHP's Local template engine compiles supported template directives into PHP and provides layout/section/include helpers. The exact directive set is implemented in framework/src/View/Local.php; it is not guaranteed to match Blade in every detail.

Common template patterns

<h1><?= htmlspecialchars($title ?? 'Home', ENT_QUOTES, 'UTF-8') ?></h1>

<?php foreach (($products ?? []) as $product): ?>
    <article><?= htmlspecialchars($product['name'] ?? '', ENT_QUOTES, 'UTF-8') ?></article>
<?php endforeach; ?>

Escape untrusted values before printing them into HTML. A template engine does not make arbitrary output safe automatically.

View engine API

  • render($view, $data = []) — resolve and render a named view.
  • compile($template) — compile supported template directives.
  • extend($layout) — choose a layout.
  • startSection($name) / stopSection() — capture a section.
  • yieldSection($name, $default = '') — output a captured section or default.
  • includeView($view, $data = []) — render an included view.

Models

Models extend LocalPHP\Model\Model and use the database manager/query builder. The example project includes User and Product models.

use LocalPHP\Model\Model;

class Product extends Model
{
    protected string $table = 'products';
    protected array $fillable = ['name', 'price'];
}

$product = Product::create([
    'name' => 'Notebook',
    'price' => 25.00,
]);

$found = Product::find(1);
$all = Product::all();
The model's actual table/key/fillable property conventions are defined in framework/src/Model/Model.php. Match those conventions to the existing implementation; do not assume every Laravel Eloquent feature (relationships, casts, timestamps, soft deletes) exists.

Database and query builder

Database access is based on PDO with exceptions enabled, associative fetches, and emulated prepares disabled. Configure credentials in .env; create the database before running migrations.

$rows = db()->table('products')
    ->select(['id', 'name', 'price'])
    ->where('active', 1)
    ->orderBy('name')
    ->limit(20)
    ->get();

$product = db()->table('products')->where('id', 1)->first();

Connection API

  • pdo() — access the PDO connection.
  • select($sql, $bindings = []) / selectOne(...) — fetch rows or one row.
  • execute($sql, $bindings = []) — execute a statement and return affected-row information.
  • insert($sql, $bindings = []) / lastInsertId() — insert and read generated ID.
  • beginTransaction(), commit(), rollBack() — transaction controls.
  • transaction($callback) — execute a callback in a transaction with rollback on failure.
  • db()->connection() — retrieve a configured connection; disconnect() clears a connection.

Migrations and seeders

Migrations are PHP files under the project's migration directory (created/used by the migration manager). Use the CLI to generate and apply them. Inspect generated migration stubs and the migration manager before writing advanced schema operations.

php local make:migration create_products_table
php local migrate
php local migrate:status
php local migrate:rollback

The migration manager tracks completed migrations and batches in its repository table. migrate:rollback rolls back the latest batch, not necessarily a single file.

Fresh migration reset

php local migrate:fresh --force
Destructive command: migrate:fresh drops tables before re-running migrations. Use --force only when you intentionally accept data loss. Back up data first.

Seeders

php local make:seeder ProductSeeder
php local db:seed
php local db:seed ProductSeeder

Seeder classes expose a run(PDO $pdo) method in the generated pattern. Seeders should be repeatable where practical, and should never contain production secrets.

Sessions and flash data

Sessions are managed by SessionManager and are exposed through the session() helper. Configuration controls cookie name, lifetime (minutes), path, domain, secure, HTTP-only, and SameSite settings.

$theme = session('theme', 'light');

flash('success', 'Saved successfully.');
$message = session()->getFlash('success');

Security features and recommendations

CSRF protection

LocalPHP checks CSRF tokens for state-changing POST, PUT, PATCH, and DELETE requests. GET, HEAD, and OPTIONS are not checked. Use a hidden field for normal forms:

<form method="POST" action="<?= url('profile') ?>">
    <?= csrf_field() ?>
    <input name="display_name" required>
    <button type="submit">Save</button>
</form>

For JavaScript requests, render csrf_meta() or a csrf_token() value and send it using the X-CSRF-TOKEN header. Failed JSON CSRF checks use HTTP 419 and the CSRF_TOKEN_MISMATCH code.

Other baseline protections

  • Prepared statements are used by the database connection/query layer.
  • The public front controller adds X-Content-Type-Options, X-Frame-Options, and Referrer-Policy headers on normal responses.
  • GET /health is available as a simple health check.
  • JSON clients can receive structured JSON 404/error responses when request headers indicate JSON.
CSRF is not authentication, authorization, validation, rate limiting, or output escaping. Protect every sensitive action with explicit access checks. Do not disable CSRF for convenience; stateless APIs need a deliberate authentication design.

Service container

The container supports bindings, singleton bindings, resolution, and binding checks. Core framework services are registered by Application.

$container->bind(ReportService::class, function ($container) {
    return new ReportService();
});

$container->singleton(Clock::class, SystemClock::class);
$service = $container->make(ReportService::class);
if ($container->bound(Clock::class)) {
    // A binding is registered.
}
  • bind($abstract, $concrete) — register a binding.
  • singleton($abstract, $concrete) — register a shared instance binding.
  • make($abstract) — resolve a service.
  • bound($abstract) — check whether an abstract is registered.

The application object exposes basePath(), router(), and version(). The current version constant is 0.2.0.

Troubleshooting

404 for all application routes

  • Confirm routes are declared in routes/web.php and use the same URI as the browser request.
  • Confirm Apache rewrite rules are enabled if using the root localhost URL.
  • Try php local serve to separate Apache rewrite issues from framework routing.

Database connection fails

  • Start MySQL/MariaDB in XAMPP or Laragon.
  • Check database name, host, port, username, and password in .env.
  • Confirm the PDO MySQL extension is enabled and the database exists.

CSRF 419 response

  • Ensure the form includes csrf_field().
  • For fetch requests, send the current token using X-CSRF-TOKEN.
  • Do not reuse a stale token after session changes.

CLI reports an unknown command

Run php local list and check spelling. Execute commands from the project root so the CLI can resolve the correct files.

Deployment checklist

  • Set the web server document root to localphp/public.
  • Never expose .env, app/, config/, framework/, vendor/, or database dumps as public files.
  • Set APP_DEBUG=false.
  • Use HTTPS and configure secure session cookies.
  • Keep CSRF protection enabled for cookie/session-authenticated browser requests.
  • Validate input, authorize every sensitive action, and escape HTML output.
  • Use prepared statements and allowlist dynamic table/column identifiers.
  • Back up the database and test restore procedures.
  • Do not use the PHP built-in server as a production server.
  • Run migrations only after reviewing their effects; back up before destructive resets.
LocalPHP is delivered as source code. Before production use, add automated tests, review error handling and access control, and perform a security review tailored to the application.
